Fixed component, modal and message schemas that rejected payloads Discord accepts, accepted payloads Discord rejects, or could not parse what Discord sends.

- **Unicode emoji on buttons and select options.** A button's or select option's `emoji` no longer needs `id: null`; `{ name: "🔥" }` validates, as in Discord's own examples. **Type change**: `Button["emoji"]` and `SelectOption["emoji"]` are now `Partial<Pick<Emoji, "id" | "name" | "animated">>`, so `id` and `name` may be `undefined`. Code that builds an emoji still compiles; code that reads `emoji.id` or `emoji.name` into a type that excludes `undefined` must handle it.
- **Text inputs inside a Label.** `label` on a `TextInput` is optional, since Discord deprecated it in favour of the wrapping Label. A modal with a text field no longer needs the deprecated field to validate. **Type change**: `TextInput["label"]` is now `string | undefined`; code that reads it as a `string` must handle `undefined`.
- **`required` on select menus.** The five select menus (`StringSelect`, `UserSelect`, `RoleSelect`, `MentionableSelect`, `ChannelSelect`) accept `required`, which Discord documents for selects in modals. It was silently dropped. **Type change**: each gains `required?: boolean`; existing code is unaffected.
- **Modal submissions parse.** `ModalSubmitData.components` is now modelled on the response structures Discord sends back (a Label wrapping its component's response, a Text Display, or, in a legacy modal, an Action Row holding a text input), not on the components a modal is created with, so a real submission parses. `ModalSubmitData` also gains `resolved`, which holds uploaded files and selected entities. New exports describe each response: `TextInputResponse`, `StringSelectResponse`, `UserSelectResponse`, `RoleSelectResponse`, `MentionableSelectResponse`, `ChannelSelectResponse`, `FileUploadResponse`, `RadioGroupResponse`, `CheckboxGroupResponse`, `CheckboxResponse`, `TextDisplayResponse`, `LabelResponse`, `ActionRowResponse`, `LabelResponseComponent` and `ModalSubmitComponent`, with a schema for each. **Type change**: `ModalSubmitData["components"]` is now `ModalSubmitComponent[]` instead of `MessageComponent`. Code that read request fields such as `style` or `label` from a submission no longer compiles; it never matched what Discord sends.
- **Select menu values on message component interactions.** `MessageComponentData["values"]` is the list of selected values as strings, which is what Discord sends, instead of select option objects. **Type change**: `values` is now `string[]` instead of `SelectOption[]`; code that read `.value` or `.label` from an element no longer compiles.
- **Embed limits.** `createMessage` and `startThreadInForumOrMediaChannel` now cap `embeds` at 10, as Discord does. `editMessage` now accepts `embeds: []`, which Discord documents as how an edit removes embeds and requires when switching a message to Components V2. No type changes.
- **Text display limits.** A single text display's `content` is limited to 4000 characters, and a modal's text displays to 4000 characters between them, matching the limit already enforced for Components V2 messages. No type changes.
- **Interaction response flags.** The message body of an interaction response only accepts the flags Discord allows there: `SUPPRESS_EMBEDS`, `EPHEMERAL`, `IS_COMPONENTS_V2`, `IS_VOICE_MESSAGE` and `SUPPRESS_NOTIFICATIONS`. Any integer was accepted before. New exports `InteractionCallbackMessageFlags` and `interactionCallbackMessageFlag`. The type of `flags` is unchanged (`number`).
- **`boundedArray` error messages (core).** An issue inside an element of a bounded array now keeps its own message. The array's length message had been applied to every nested issue without a message of its own, so a missing field deep in a component tree was reported as an array length problem. Which inputs pass or fail is unchanged, and the signature is unchanged.
